# gRPC → REST Endpoint Mapping (Draft)

Companion to [`REST_MIGRATION_PLAN.md`](REST_MIGRATION_PLAN.md) (Phase 1.3, per-domain controllers), scoped to issue
#600.
Draft for discussion - no implementation yet.

An `unused` badge at the start of a note means the gRPC method is implemented but not called by
the frontend (per `api-calls-report.md` -> `scripts/compare-api-calls.js`). We need to decide
whether we should add them as REST endpoints, if they aren't even used.

All paths are relative to `/api/v1`.

**Resource-nesting rule (decided):** default to REST-ful nesting under the owning resource -
`/projects/{projectId}/members/{userId}`, not a flat `/project-members`. A domain only gets pulled out
into its own flat, top-level base path when either (a) the request genuinely doesn't carry the
parent ID, so nesting isn't possible (e.g. `AcceptProjectInvitation`, keyed only by an opaque
token), or (b) it's a deliberate choice to keep a controller's scope small and self-contained
even though the resource *could* nest (currently just `Export`, kept off `/projects` on purpose).
Any other flat-looking path in this table should be treated as a candidate for the same scrutiny.

## Blockers

These must be cleared before the mapping is implemented. Each one changes the service layer,
not just the REST layer.

1. **Project status transitions need a state machine** (blocks `PUT /projects/{projectId}/status`).
   `ProjectService.validateProjectUpdate` only checks which transitions are allowed out of
   `ARCHIVED`. From `ACTIVE` or `ACTIVE_LOCKED`, a requested `CLEARED` passes the check and is
   saved, and the project then disappears from every list for good. gRPC can't send `CLEARED`,
   but the REST body takes the native `ProjectStatus` enum, so it can. Invalid transitions are
   also rejected with `require(...)`/`error(...)`, which `RestExceptionHandler` does not map, so
   REST answers 500 instead of 400. The state machine should define the allowed transitions and
   reject the rest with a `SnowballRException`.
2. **Project listing needs one service query with optional filters** (blocks `GET /projects`).
   The `userId`/`status` filters are backed by four separate service calls that don't line up
   with them (see the `GetAllArchivedProjectsForUser` note).
